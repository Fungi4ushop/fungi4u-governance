# Decisions

Purpose: record *why* things are built the way they are, so a decision doesn't get accidentally reversed by someone (including a future AI session) who wasn't there for the reasoning. Plain chronological list — no IDs, no formal approval process, no versioning ceremony. Add a short entry here whenever future-you or a successor would otherwise have to guess "why is this like this?"

---

**2026-01-26 — Stock ledger is append-only.** Rows are never edited or deleted, only added. All stock movement goes through SQL functions, not direct table edits. Historical truth must never change after the fact — if a mistake is made, correct it with a new entry, not by rewriting history.

**2026-01-26 — Physical safety logic runs locally, on the device, not in Home Assistant.** Home Assistant is a supervisory/monitoring layer, not the authority. If the network, Supabase, or Home Assistant goes down, the climate control hardware must keep enforcing its own safety limits regardless. Manual override must always be physically possible.

**2026-01-26 — The three domains (economic ledger, biological tracking, physical processing) are kept separate and must not be mixed.** Yield is calculated from measured values only, never estimated in the UI.

**2026-05-30 — Originally planned: Senseair S8 (via ESPHome) as the primary CO2 sensor; Inkbird as secondary/verification only.** The Senseair S8 was never actually installed — superseded before installation by the DFRobot SEN0659 RS485 CO2 sensor (see the 2026-07-06 entry below), which is the one actually wired in and providing the "CO2" entity in Home Assistant. The secondary/verification-only role for Inkbird still stands, just with SEN0659 as the primary sensor instead of the originally planned Senseair S8. Do not treat Inkbird readings as authoritative, and do not block operations on the Inkbird bridge being up.

**2026-01-26 — Environmental control priority when conflicts arise: Temperature > CO2 > Humidity.** Humidity may drift from target to protect temperature; CO2 control normally takes priority over temperature, but an approved temperature safety limit always wins over a CO2 target. Full reasoning in `MICROCLIMATE.md`.

**2026-01-26 — Fresh air is introduced into the plenum and mixed before reaching the room, not injected directly.** Chosen to reduce direct airflow disturbance on the mushrooms and to support future CO2 management. The original direct-injection fan is retired in favor of this approach.

**Date unknown (before 2026-06-26) — Replaced the Sonoff-based relay switching with a ULN2803 relay driver subsystem.** The old Sonoff wiring (W8–W17) is fully retired; see `HARDWARE_REFERENCE.md` for the current relay wiring. If you find any reference to Sonoff relays elsewhere, it's stale.

**2026-07-06 — Inkbird bridge's Tuya protocol version corrected from 3.5 to 3.4**, matching the device's actual firmware (confirmed via the LocalTuya integration's stored diagnostics). This was silently causing every connection attempt to fail. — **⚠️ WRONG, REVERSED 2026-07-19. The device is 3.5, not 3.4.** Proven by probing every Tuya version against the live device from inside the add-on: only **3.5** returns a valid `dps` payload (`{'2': co2, '18': temp, '19': humid}`); 3.4 returns Err 914 "check device key or version". So the 3.4 "fix" was itself the bug that kept the bridge dead. The code is back to `set_version(3.5)`. Lesson: the LocalTuya "stored diagnostics" that justified 3.4 were not verified against a live read. See the 2026-07-19 Inkbird entry below.

**2026-07-06 — Chose DFRobot SEN0659 (RS485 CO2) and SEN0438 (RS485 temp/humidity) to replace the DHT22 pair.** Both confirmed as the actual sensors, register maps and addressing documented in `HARDWARE_REFERENCE.md`. The CO2 UART reservation (TX2/RX2) is kept, but its reasoning changed: it's no longer earmarked for a specific planned sensor (the new CO2 sensor is RS485, sharing the TB12 bus with the temp/humidity sensor instead) — it's now just a low-cost hedge in case a future sensor is needed and buying another RS485 device isn't worth it.

**2026-07-07 — RS485 sensor addressing: CO2 sensor stays at its factory default Modbus address (`1`); the temp/humidity sensor's DIP switch was set to address `2` instead of changing the CO2 sensor's address in software.** Originally planned the other way round (leave temp/humidity at its assumed factory default, reassign the CO2 sensor's address via a Modbus register write), which would have needed a USB-RS485 adapter and a one-time isolate-one-sensor-at-a-time commissioning step. Simpler to just give the DIP-switch-only sensor a free address, since it requires no adapter, no software write, and no temporary rewiring — both sensors go straight onto the shared TB12 bus together. Also discovered while doing this: the temp/humidity sensor ships with all 8 DIP switches OFF (address `0`, the Modbus broadcast address), not address `1` as `HARDWARE_REFERENCE.md` had assumed — don't trust that "likely factory default" claim for other units of the same sensor without checking.

**2026-07-07 — Both new RS485 sensors share a single terminal block (TB7) and a single 4-wire bus, rather than one terminal block each.** Physical panel space made adding new terminal blocks impractical, and TB12 (the RS485 bus terminal) only has 2 positions — never sized for power — so it couldn't host both signal and power on its own. Since both sensors already tie together electrically on one shared bus (same A, same B, and now a shared fused 12V branch too), there was no need to run 8 separate conductors: one twisted pair carries shared A/B, another carries shared V+/GND, reusing the existing LAN (Cat5e) cable already run to TB7/TB8 for the old DHT22 pair. Consequences: TB7 was repurposed (superseding its original "stays installed unused" plan — the DATA/VCC wiring and its 10k pull-up resistor were removed to make room for the new function), TB12 is now genuinely spare (RS485 transceiver leads relocated there from TB12), and TB8/DHT22 Sensor 2 was left untouched rather than also being repurposed, since only one terminal block was actually needed. Fuse 6 (0.5A) added to protect this new 12V branch, sized from DFRobot's published current draw for both sensors (combined < 30mA). Full wiring detail in `stock-control/docs/HARDWARE_REFERENCE.md`. Physically wired 2026-07-07; validated working 2026-07-09 (see entry below for what stood between wiring and validation). (A standalone installation PDF was generated at the time but dropped 2026-07-09 once it had drifted from `HARDWARE_REFERENCE.md`'s subsequent updates — treat `HARDWARE_REFERENCE.md` as the sole source of truth, don't recreate a second wiring document that can go stale again.)

**2026-07-09 — The RS485 sensors don't work through ESPHome's stock `modbus_controller:` component; the firmware now polls them with a hand-written raw-UART lambda instead.** Root cause, after several days of troubleshooting: the installed RS485 transceiver module (confirmed by an identical replacement — not a hardware fault) echoes its own transmitted query back onto the receive line, immediately followed by the real reply, with no gap between them. ESPHome's built-in Modbus framing can't tell the two apart and discards both. The fix: `fruiting-room-controller.yaml`'s sensor polling reads raw bytes directly from the `uart:` component, skips the known fixed 8-byte echo, then parses and CRC-validates whatever follows. Two dead ends explored first, worth knowing about so they're not repeated: (1) the module's `TXD`/`RXD` pad labels look backwards at first glance (its `TXD` pad is actually an input, `RXD` an output) — the original wiring was actually correct, a software pin swap during troubleshooting just produced a more confusing symptom (self-echo instead of silence); (2) a spare replacement transceiver was bought suspecting a hardware fault — not needed, kept uninstalled as a spare. Full technical detail in `stock-control/docs/HARDWARE_REFERENCE.md`'s "RS485 transceiver notes" section — if this ever needs touching again, don't reintroduce `modbus_controller:` for these two sensors, it will silently fail the same way.

**2026-07-09 — The two RS485 sensors are wired as a daisy-chain through two ceiling junction boxes, not a single shared splice, and the signal pair changed from Blue/White-Blue to Green/White-Green.** Originally planned (2026-07-07) as one splice point where both sensors' A/B/V+/GND leads all join the field cable together. In practice, each sensor got its own sealed junction box at the ceiling (sensor hangs below its box), and each of the field cable's 4 conductors runs as a single wire from TB7 through the first box — where that sensor's matching lead taps in — continuing on to the second box, where the second sensor taps in too. Electrically this is the same shared bus/branch either way (both sensors' A's tied together, etc.), but physically it's a two-stop chain, not a star — matters for troubleshooting, since a break could be on either segment, not just "the splice." Separately: the original Blue/White-Blue signal pair developed a wire break during commissioning and was abandoned rather than re-spliced — signal now runs on Green/White-Green instead (Green = A+, White-Green = B−), with Blue/White-Blue now spare alongside Brown. Full detail and the lead-by-lead wiring table in `stock-control/docs/HARDWARE_REFERENCE.md`.

**2026-07-09 — DHT22 Sensor 2 (TB8/GPIO33) removed from the firmware, decommissioning the last of the DHT22 pair, now that both RS485 sensors are validated.** Wiring left physically in place for now — operator's choice, not a plan to revisit it, just not urgent enough to do the same day. GPIO33 is free but not yet reassigned to anything.

**2026-07-09 — RS485 sensor parsing changed from "skip a fixed 8-byte echo" to "scan for a valid CRC-correct frame wherever it starts."** The transceiver's self-echo (see the entry above) turned out not to be consistent — some queries come back with the echo, some don't, observed on the same hardware within the same session. The fixed-offset fix broke silently (values went to "unknown" in Home Assistant, no error) the first time a reply arrived without an echo prefix, since it was chopping real data off assuming an echo that wasn't there. The robust version scans the received buffer for a frame matching the expected address/function/byte-count with a correct CRC, regardless of what precedes it. If this component is ever touched again: don't reintroduce a fixed-offset assumption, this hardware doesn't support one.

**2026-07-09 — Documented the external relay multiplug for the first time; it wasn't in `HARDWARE_REFERENCE.md` before, despite already existing.** All four ULN2803 relay channels (TB3/TB4/TB5/TB13) extend via an 8-pin cable to an operator-built external box, rather than switching mains loads directly at the panel — 230V mains input like a normal power strip, one internal 12V relay per outlet (coil energized via 12V passed from the controller), and a 3-position manual override switch per outlet (off/auto/manual-on). This is where `SAFETY.md`'s "manual override must always be physically possible" is actually implemented for these four loads. Came to light because the humidifier and light were plugged into each other's sockets, producing a confusing exact-inversion symptom (HA showing each switch's state opposite to physical reality) that got chased as a possible relay wiring fault before the real, much simpler cause was found. Fixed by re-plugging into the correct sockets (socket 2 = humidifier/TB4, socket 3 = lights/TB5) — no wiring or software change needed. Full socket-to-channel mapping in `HARDWARE_REFERENCE.md`'s "External relay multiplug" section.

**2026-07-10 — Removed the end cap from the fruiting-room supply duct, abandoning the distributed-hole-only design as the current airflow strategy.** The originally designed 10mm hole pattern along the sealed duct wasn't giving enough control over CO2 and humidity in the fruiting room. Leaving the duct end open (rather than capped with holes only) is what currently determines airflow/pressure behavior in the room. This is an acknowledged interim workaround, not a redesign decision — full duct hole-pattern validation is still an open question (see `MICROCLIMATE.md`).

**2026-07-10 — The plenum's fresh-air fan isn't ducted directly to the outside; it draws its outside air indirectly, via a 15mm hole in the grow room's external (rear) dry wall.** Outside air enters through that hole, passes through the grow room (picking up that room's aircon-conditioned temperature and whatever CO2 is already present there), then gets pulled into the plenum. So the fruiting room does receive genuine outside air for CO2 dilution, just restricted to a small opening and already tempered/mixed by the grow room first, rather than via a dedicated straight-outside duct. See `MICROCLIMATE.md`'s "Fresh air" section.

**2026-07-10 — Added a grow-room temperature/humidity DHT22 (monitoring-only) on the existing TB8/GPIO33, and fixed the circulation/fresh-air fans' restore behavior after finding they defaulted to off on reflash.** Bench-tested a spare DHT22 (two on hand) on TB8 before running the permanent 2-3m cable to the grow room — confirmed TB8's actual wire-to-position mapping in the process (TB8-1=DATA/W46, TB8-2=spare/W47, TB8-3=VCC/W48, TB8-4=GND/W49), which hadn't been documented at that granularity before (see `HARDWARE_REFERENCE.md`). Purpose: this sensor exists to see what the plenum's fresh-air fan is actually drawing in from the grow room (see `MICROCLIMATE.md`'s "Fresh air" section) — informational only, not a control input, so no failover/authority logic attached. Separately, reflashing `fruiting-room-controller.yaml` for this exposed that ESPHome's `fan:` component defaults `restore_mode` to `ALWAYS_OFF` — the circulation and fresh-air fans (previously manually set to 81%/79%) came back off after the flash, silently working against the room's core "continuous circulation" design bet. Fixed by setting `restore_mode: RESTORE_DEFAULT_ON` on both fans; confirmed on the next reflash that they now restore their last-known speed automatically. If this component is touched again: don't leave fan `restore_mode` unset, it isn't safe to assume ESPHome's default matches this room's design intent.

**2026-07-11 — Phase B ledger cleanup/hardening, and the harvest data model (captured from the real process).** Phase B (see `stock-control/docs/LEDGER.md`) proceeded in verified migrations: dropped 9 dead/orphaned objects; moved to an **RPC-only security model** (RLS on all base tables, four narrow SECURITY DEFINER wrappers + two read views as the only anon-accessible surface, internal functions revoked from PUBLIC — verified against a local stack that direct table access and internal functions return 401); decoupled `human_actors`/`stock_reason_codes` from `auth.users`. Then a **harvest redesign**, driven by the real process finally being described:
- **Harvest is not one event.** Mushrooms are picked repeatedly as each is ready over several days, and cold-stored just above freezing until there's enough to process. So a "flush" is *many pickings*, not a single weight.
- **Decisions (operator, 2026-07-11):** record **per picking** (finest data); a new **`harvest_pickings`** biological table holds each picking, which *also* posts a raw-IN `HARVEST` ledger event (biology and economics stay separate but linked); **flush number is inferred** from the rest-gap between pickings (a >4-day gap starts flush 2; never a flush 3, since bags are removed after two); **processing consumes the entire accumulated raw balance** (not a typed weight); **cold storage is not tracked as a separate location** — there's one raw bucket, so splitting it would add nothing (the `FRUITING_ROOM` location code is now a legacy label for that single raw bucket).
- This replaces the old single-number `flush1_grams`/`flush2_grams` columns (not append-only, untimestamped, and disconnected from the raw-stock ledger — which is why processing/sale couldn't work) and the hard-coded `192000` biological-yield. Increment 1 (per-picking capture + gap inference + raw ledger posting) is built and verified; the processing rework, retiring the old flush columns, and the panel changes remain.

**2026-07-11 — Database schema changes go through committed git migrations only; direct access (CLI, dashboard, or an AI-session MCP) is for inspection and authoring migrations, never for mutating the live schema.** Rationale: the live Supabase schema had drifted entirely out of version control (see `stock-control/docs/LEDGER.md`) — the objects the app depends on exist only on the live instance, almost certainly because they were created directly via the dashboard/SQL editor rather than through migrations. A standing write/DDL path to production (such as an authenticated Supabase MCP) would make it easy to recreate exactly that failure. So MCP and the CLI are treated as convenience tooling for AI-assisted sessions, **not the system's foundation.** The durable, succession-surviving stack is: migrations in git (schema/reproducibility), the app's anon key + RLS (runtime), and Bitwarden (credentials) — a successor inherits those regardless of whether they ever use AI tooling or MCP.

**2026-07-11 — Cellular alarm device: 4G/LTE only (hard constraint), leading candidate the Interlynx S150.** The GSM alarm dialler from the monitoring-architecture entry below must be 4G/LTE — not a 2G/3G unit. Reason: South Africa must complete its 2G/3G shutdown by end-2027, and MTN plans to switch off 3G by end-2026, so a 2G-only "GSM" dialler (most of the cheap market) would be a dead-end purchase. Leading candidate: the **Interlynx S150** (GSM 3G/4G SMS Remote Controller Alarm, 8 digital inputs + 2 relay outputs, https://interlynx.co.za) — it matches every requirement: inbuilt rechargeable backup battery with an external-power-monitoring alarm (the power-loss-on-the-controller's-breaker function), 8 digital inputs (the ESP32 drives one for environmental alerts, 7 spare), and SMS to 3 numbers (calls up to 5). Before ordering, confirm three things: (1) order the 4G module explicitly — 3G/4G is optional on the S150, so the default may ship as 2G; (2) confirm the 4G LTE bands cover MTN/Vodacom SA (B1/B3/B7/B8 minimum); (3) get a price (not published — needs a quote). Local alternative considered and set aside: PicC Electronics (smsalert.co.za, an SA manufacturer with guaranteed local bands) splits the job into two separate products (power ~R2,400 + temperature ~R3,600 ≈ R6,000), against the single-device design — worth a call only if local-manufacturer support outweighs consolidating to one box. Not yet purchased; the choice is provisional pending the quote and band confirmation.

**2026-07-11 — Settled the fruiting-room monitoring/alarm architecture, and its boundary against the power/solar workstream.** Context: the operator wanted a reliable alert when the crop is at risk, after finding the Home Assistant phone push unreliable (it depends on the router + internet, and internet drops during a power outage).

Boundary (this is the corrected version — an earlier draft wrongly filed the power-availability alarm under the power workstream):
- **The power monitoring & automation workstream (future `docs/SOLAR.md`) is source-only** — solar generation, battery state-of-charge, inverter health/optimization. It is NOT responsible for telling the climate system whether it has power.
- **Monitoring whether the climate controller itself has power is part of the CLIMATE CONTROL system**, not the power workstream — it's the climate system's own liveness/watchdog concern, same category as "is temperature too high." Each system monitors its own health; the climate system must not depend on the power workstream existing in order to know its own controller has gone dark.

Facts that shaped it:
- Everything (Pi, router, fruiting-room controller, fans, humidifier) is on the inverter/battery, so the crop already survives a normal mains outage — climate control keeps running. Mains loss is therefore NOT an alarm condition (alarming on it would cry wolf every outage).
- The real alarm conditions are (a) loss of power to the climate controller itself — battery flat, or a breaker trip / wiring fault on the controller's own circuit — and (b) an environmental excursion (temp/CO2/RH out of range).
- These outages are rare, unexpected and local (not scheduled load-shedding); during them the fibre internet is down but the cellular network stays up — so alerts must go out over cellular, not the internet.

Settled design (agreed, not yet built):
- **A single GSM alarm dialler is the climate system's cellular-out device.** Battery-backed, stores 3 recipient numbers (operator's requirement: more than one phone), wired onto the SAME circuit breaker as the fruiting-room controller.
- **Hard requirement — same breaker as the controller:** this makes the device a faithful proxy for "does the controller have power?" On a different breaker, a trip/fault on the controller's own circuit would silently stop climate control while the monitor reported all-clear. On the same breaker it loses power exactly when the controller does; its internal battery then sends the power-loss SMS over cellular. (This is compatible with the source/climate separation above: the device stays functionally independent — own battery, own SIM, own logic — it just shares the controller's power circuit so it monitors that circuit honestly.)
- **It carries both alarm types:** power-loss (native mains-fail behaviour on its own input) and environmental (the ESP32 evaluates temp/CO2/RH thresholds locally in firmware — so it works even when HA is down — and closes a spare relay into one of the dialler's zone inputs).
- **The local buzzer (previously planned) is dropped.** Its only justification was an internet-independent local alert; the cellular device supersedes that on every axis (also internet-independent, and reaches the operator anywhere rather than only within earshot), so a separate buzzer would be redundant hardware — against the project's no-overengineering rule.
- **The Home Assistant phone push is retained as a best-effort extra** when everything is up (richer info, no added hardware) — but is explicitly not relied on, since it dies with the internet.

Near-term build work: source a 3-number GSM alarm dialler, wire it onto the controller's breaker, move the environmental threshold logic into `fruiting-room-controller.yaml`, and drive a dialler zone input from a spare ESP32 relay output.

**2026-07-11 — Replaced the home's main router (D-Link) with a TP-Link (hardware model EX511, an extender used in router mode); repurposed the old D-Link as an Ethernet-backhauled WiFi extender near the garage.** Driven by needing a reliable phone-notification path for the microclimate alarm automation (see the 2026-07-10 alarm entry above) — the D-Link had a mesh-roaming bug causing frequent "connected, no internet" on phones. Root cause chain found during troubleshooting:
- The TP-Link's 2.4GHz radio itself turned out to be flaky (channel congestion from neighboring networks on multiple channels, and possibly a firmware issue specific to this extender-as-router hardware) — a manual channel change and reboots didn't fully fix it, and it's not worth chasing further given a working alternative exists.
- **The Home Assistant Raspberry Pi was riding this same flaky 2.4GHz band**, and went completely unreachable partway through the router changes — discovered by checking the TP-Link's own wireless/wired client lists and finding the Pi absent from both. Fixed by wiring the Pi to Ethernet instead, since it sits right next to the router anyway. This is a deliberate reliability upgrade, not just a workaround — HA is core infrastructure for this whole project and shouldn't depend on a wireless band already known to be unreliable.
- **Home Assistant's IP changed from 10.0.0.22 to 10.0.0.110** as a side effect of switching from WiFi to Ethernet (new MAC address, new DHCP lease). Claude Code's MCP server config (`~/.claude.json`) was updated to match. **A DHCP reservation for the Pi's new Ethernet MAC is recommended** so this IP doesn't shift again on a future reboot — not yet done.
- The fruiting-room ESP32 is believed to connect via the D-Link extender's WiFi (it sits near the grow room, closer to the extender than the main router) — reachable again after the dust settled, but not yet confirmed which access point it's actually associated with.

**2026-07-15 — Solar/inverter telemetry into Home Assistant will be read locally over Modbus RS485, not via the Sunsynk cloud API.** Consistent with the house-wide principle that monitoring/telemetry shouldn't depend on the internet (same reasoning as the 2026-01-26 local-safety-logic and the 2026-07-11 alarm-architecture entries). Concretely: a Waveshare RS485-TO-ETH gateway on the inverter's BMS-port RS485 (pins 1=B, 2=A), shared with the battery's CAN via a 2-in-1 splitter, feeding the kellerza Sunsynk add-on → the existing Mosquitto MQTT → HA. Key facts that made this clean, all verified 2026-07-15: the inverter is a Sunsynk **SG01LP1** (Modbus ID `1`, confirmed on the LCD) whose local RS485 is a *separate interface* from the round COM/RS232 port the WiFi datalogger uses — so **the local read coexists with the Sunsynk Connect app** (no need to sacrifice the phone app). Only the *card* (Sunsynk Power Flow Card, a HACS frontend) was installed in HA, with no data behind it. **Deferred on cost the same day** — fully scoped, nothing bought. Full spec, pinout and shopping list in `stock-control/docs/SOLAR.md`. If this is ever revisited: don't reach for the cloud integration as a shortcut without re-reading why local was chosen.

**2026-07-16 — The fresh-air (FAE) fan moved from manual speed to automatic closed-loop CO2 control, on the ESP32.** ⚠️ **The energy premise in this entry was measured wrong and is corrected by the 2026-07-17 entry below — the aircon does *not* draw 867 W continuously; the whole room draws 11.32 kWh/day. The change itself stands (it did not cause the 2026-07-16/17 RH event — a failed circulation fan did), but its savings case is roughly 2× overstated.** Why: with the inverter now readable in HA, measurement showed the fruiting-room **inverter aircon draws ~867 W essentially continuously** (~90% of the room's electricity, and the bulk of the whole property's ~R3,200/mo grid bill) — and because it's an inverter (already-efficient) unit, the only way to cut its energy is to reduce the *heat it fights*, a large part of which is warming the cold winter fresh air the FAE fan pulls in. The room was over-ventilating (CO2 ~628 ppm at 55% fan, well below grey-oyster tolerance), so a proportional CO2→fan loop was added to `stock-control/esphome/fruiting-room-controller.yaml` to bring in *only as much* fresh air as needed to hold a CO2 target — minimum ventilation = minimum aircon heat load, adaptively and 24/7. **Put on the ESP, not HA, deliberately** — same local-control principle as the 2026-01-26 safety-logic entry: it must keep working if HA/network drops, and it survives reflashes (unlike a manually-set HA fan speed). Design: proportional band (`substitutions:` `co2_target` default 750 ppm, tune upward while watching cap quality), bounded 40–85% (never off → baseline FAE; never slams to max), **temperature has priority over CO2** (room below `temp_floor` 14 °C → fan forced to floor, so it never fights the aircon into a cold room, per `MICROCLIMATE.md`'s Temp > CO2 rule), and the loop runs only on a valid CO2 read (a dead sensor freezes the fan rather than ramping it). Consequence: **manual HA fresh-fan changes are now overwritten within 30 s** — that's intended. Watch on the first flush: CO2 settling near target, and RH (less dry fresh air can push humidity up — blotch risk if it sits >95%, since there's no active dehumidification). The circ fan stays manual (internal mixing only, no effect on heat loss). **Deployed and verified live 2026-07-16**: the fan tracks CO2 exactly per the proportional formula (e.g. CO2 664 ppm → fan 43%), stable, easing ventilation from the old fixed 55%. The RH-high alarm was lowered 98% → 95% beforehand as the safety net. **Flash incident (documented in `stock-control/docs/HARDWARE_REFERENCE.md`, "Flashing the controller"):** the flash itself went fine, but it was built against a fresh ESPHome dashboard whose `secrets.yaml` had the wrong WiFi SSID (`pret208-4.2G` instead of the extender `pret208-ext`), so the device dropped into fallback-AP mode and went dark on the LAN for ~2 hours — recovered via the "Fruiting Room Fallback" captive portal. Lesson: verify `secrets.yaml` WiFi creds before any controller flash.

**2026-07-17 — The fruiting room's fans are the WRONG PART: marine bilge blowers rated 600–700h intermittent duty, run 24/7. This is the root cause of the low-RH event of 2026-07-16/17.** Recorded in full because the *diagnosis* was far harder than the fault, and because the blind spot that hid it still exists.

**The fans are SEAFLO SFIB1-130-01 — 12V marine *bilge blowers*** (3"/76mm, 130 CFM / 220 m³/h, 2.5A, sealed motor shaft, ISO 8846). A bilge blower ventilates a boat's engine bay for a few minutes before you start the engine. **SEAFLO rates them at 600–700 hours, intermittent — ~3h/day average** (manufacturer FAQ: https://www.seaflo.com/index.php?m=home&c=Lists&a=index&tid=354). **This system runs them 24/7 = 720 hours/month, so the entire rated life is consumed in about one month.** The failed fan lasted a few months (~2,000+ hours) — **~3× its rating. It over-performed, then wore out.** Nothing was defective; the part was simply never meant for this.

**What happened:** the fan wore out gradually *while running*, and kept running, because a spinning motor keeps spinning — it loses **starting** torque, not running torque. Nothing looked wrong. Then the **2026-07-16 13:52 reflash rebooted the ESP32**, PWM dropped to zero, and the fan stopped. Worn out, it could not restart. It stayed dead ~24 hours. **The reflash broke nothing — it just stopped the fan once, and that was enough.** Symptoms on the bench: needed a manual spin to start, then ran slow; bearings free by hand; **cleaned and still faulty on a direct 12V supply** (ruling out MOSFET1, wiring and connectors). That is a worn-out motor, not a dirty one.

**Why nobody noticed:** both fans are **2-wire, speed-set by chopping the ground with a MOSFET — no tacho, no current sense, no feedback of any kind.** Home Assistant displayed "82%" throughout, because that is the *commanded* PWM. **HA cannot tell a spinning fan from a dead one, and `restore_mode: RESTORE_DEFAULT_ON` restores the PWM setting, not the rotation.** The room lost circulation, RH fell ~90% → ~80%, the humidifier pinned at 100% duty unable to win, and `rh_low` fired ~20 hours later — pointing at humidity, a *symptom*. Full detail and replacement spec: `stock-control/docs/HARDWARE_REFERENCE.md`, "Fan failure mode: WRONG FAN FOR THE JOB".

**⚠️ Correction to the first version of this entry (commit `647234b`/`f678543`): it recorded the cause as "spore fouling". That was wrong.** The fan came out covered in grey-oyster spores and that anchored the diagnosis — but everything in that airstream is covered in spores, and the blower has a **sealed motor shaft and corrosion-resistant housing precisely because it is built for wet bilges**. It also failed while mounted in the **grow room at ~65% RH**, not the fruiting room's 97%. **The spores were incidental; the duty cycle was causal.** The real answer was in the part number all along and surfaced only when sourcing a replacement. **Lesson: look up what a component actually is before theorising about failure mechanisms.** A plausible mechanism is not evidence.

**What the fault was NOT** (each ruled out by measurement — recorded so a successor doesn't re-walk them):
- **Not temperature.** A 5-day baseline killed the first theory: 07-11→07-15 held **RH 90.2% every single day**, and 07-14/07-15 averaged **16.8 °C — the same as the event days at 17.0 °C**. Same temperature, nine points less RH.
- **Not the 2026-07-16 FAE/CO2 change.** It moved the fresh-air fan 55% → ~50% — a 5% ventilation change cannot move RH nine points, and *less* ventilation should *raise* RH.
- **Not the humidifier, reservoir, float valve, feed pipe, or the humidifier's own level switch.** Hours went into these. All were working. The humidifier was correctly misting into a room no longer receiving its output.
- **Not the RH sensor** (temperature comes from the same Modbus frame and stayed correct), **not the relay sockets** (1 and 4 off all five days), **not the MOSFET/wiring/connectors** (direct-12V test).

**What actually cracked it — all physical observations, none of them telemetry:** "lots of spores on it", "I have to manually turn it to start, then it runs slow", bearings free by hand, the direct-12V test, and finally the part number. **The telemetry only ever showed what was commanded, never what was happening.**

**Diagnostic method worth reusing: use absolute humidity, not RH.** RH conflates moisture with temperature and hides the signal. Absolute humidity (g/m³, from RH+temp) isolated it immediately: **12.9 baseline → 11.4 during the outage → 12.35 once the return duct was sealed**. It also exposed that, with the dead fan sitting in an *open* return duct, the plenum was bleeding humidified air backwards down the duct and out through its distributed holes into the **grow room** — sealing the duct alone recovered most of the loss.

**Decisions taken:**
- **Do NOT replace like-for-like.** An SFIB1-130-01 in a 24/7 position is a ~1–3 month consumable, forever, in both fan roles. **The single criterion for a replacement is a continuous-duty rating** — such fans are typically **30,000–70,000 hours, i.e. 3.5–8 years instead of one month.**
- **Circulation fan → RAM Mixed-Flow Inline 100mm** (199 m³/h, 23/26W, 220–240V, 2-speed, ~R890–970). Chosen because **mixed-flow gives static pressure**, which the 110mm PVC ducts with distributed 10mm holes actually need — a plain axial fan won't match a blower there. **100mm is also a better fit than the 76mm SEAFLO**, which necks the 110mm duct down and has been strangling it. It is mains, so it goes on **free multiplug socket 1 or 4** — the circ fan is fixed-speed and unautomated, so nothing is lost and **no firmware change is needed**. **Do not size up to 150mm** because it's the size in stock: 580 m³/h into a duct designed around 220 contradicts `MICROCLIMATE.md`'s "continuous, low-velocity, no direct airflow on the mushrooms" bet.
- **The two fan positions are no longer interchangeable — buy one, not two.** This supersedes "one spare covers both". **Fan 2 (fresh air) runs the proportional CO2 loop (40–85%) and a 2-speed mains fan cannot do that** — it needs a continuous-duty **12V** brushless (keeping the MOSFET/PWM wiring) or an **EC fan with 0–10V input** (ESP32 PWM + RC filter — a project). **Unresolved**, and it matters: that fan is the same worn-out model, well past 600–700 hours, **and is currently the room's only fan**. Keeping one SEAFLO as an emergency spare for that position is reasonable only until this is solved.
- **RPM feedback remains the fix for the blindness, and is queued, not done.** A 4-pin PWM fan with tacho on **GPIO21 (free)** makes this alarmable instead of invisible; needs W30–W35 rewired plus a firmware change. Fold it into the Fan 2 rework, since that position is being redesigned anyway.
- **Until then, physically confirm both fans are turning after any reboot, reflash or power event.** This is now the single most important post-flash check. Do not trust the HA percentage.

| **Aircon** | **~7.6–8.0** | **~70%** |

**2026-07-17 — Added humidifier duty-cycle sensors and a "struggling" alarm in Home Assistant, as a LEADING indicator.** The humidifier relay is only ever on or off, which hides *how hard* it is working. The ESP32 runs simple hysteresis (on <88% RH, off >92%), so healthy operation cycles at ~50% duty; sustained ~100% means it is commanded on and cannot reach the off-threshold. In this event duty pinned at 100% at 13:52 — **~20 hours before RH fell far enough to trip the <80% `rh_low` alarm**. Built as HA `history_stats` sensors (`sensor.humidifier_duty_1h` / `_24h`) plus an automation firing above 90% for 1h, and a "Fruiting room" dashboard with green/yellow/red gauges (green <70, yellow 70–90, red >90). Put in HA, not the ESP32, deliberately: it is *monitoring*, not control (per `SAFETY.md`), so it needs no reflash and cannot affect the room if HA is down. Mirrored for reference in `stock-control/home-assistant/humidifier_duty_sensors.yaml` — **that copy does not run**; the live config is on the Pi.

**Known limits of this instrument, both learned the same day:** (1) it measures what the ESP32 **commands**, not what the humidifier **does** — the humidifier has its own internal level switch, so it can be cut off while the relay still reads "on"; and (2) HA numeric triggers are **edge-triggered**, so the alarm did not fire for the event in progress (duty was already 100% when it loaded) — the same trap that silently disarmed the CO2 leg on 2026-07-15. It is armed for the next occurrence.
